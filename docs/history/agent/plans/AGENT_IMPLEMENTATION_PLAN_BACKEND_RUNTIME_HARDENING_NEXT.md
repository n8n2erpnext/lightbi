# Implementation Plan: Backend Runtime Hardening Next

## Goal
Now that the Understanding layer successfully generates actionable opportunities (e.g., `Revenue over Time Period` for `good_finance.csv`), we must fix the massive disconnect at the Execution layer. Currently, the system hallucinates a backend execution path that immediately fails and silently falls back to a limited Javascript sandbox, rendering complex SQL useless. This phase will solidify the compile constraints and orchestrate a genuine local execution path instead of a mock HTTP stub.

## 1. Reality Check: The Current Execution Paths
Before modifying code, we must acknowledge the actual structure:
- **`Investigation.tsx` Calling Order**: It first calls `executeBackendPreview`. If that fails, it catches the error and silently drops down to `executeDuckDBPreviewSandbox` using local `rows` data.
- **Role of `backend-preview-executor.ts`**: It does **NOT** run DuckDB WASM or mount files. It merely executes a `fetch` POST to a phantom API (`/api/preview/execute`). Because this endpoint doesn't exist, it universally fails with "Network failure".
- **Role of `duckdb-preview-sandbox.ts`**: This is the JS fallback. It ignores SQL entirely and uses rudimentary Javascript array `.filter()` and `.reduce()` methods to build charts. It cannot handle complex operations like truncating dates or joining logic.
- **Role of `duckdb-preview-runtime.ts`**: Currently an isolated **MOCK**. It generates fake random data (`Mock label 1`, `Math.random()`) and is not connected to the actual local execution flow.
- **Where the Failure Happens**: 100% of execution failures occur identically: `backend-preview-executor.ts` fails to find the API -> silent fallback occurs -> JS sandbox receives complex intent -> JS sandbox cannot process advanced temporal/dimension groupings -> Preview fails or shows limited data.

## 2. Top 2 Backend/Runtime Failures to Address
1. **SQL Compilation (Dialect/Syntax) Immaturity**: Even if we connect a real backend, the SQL generated by `safe-sql-preview.ts` has never been tested against a strict engine. It likely contains generic SQL flaws (missing identifier quotes, invalid date-truncation dialect) that will instantly crash DuckDB.
2. **Orchestration / Phantom Fallback**: The `backend-preview-executor.ts` path is a phantom stub. The failure is not a WASM mount error; the failure is that the system defaults to a network `fetch` instead of utilizing a real local DuckDB executor. This orchestration must be replaced or hardened to stop the silent, guaranteed fallback.

## 3. Scope & Boundary
- **Compile/Generate SQL Issue**: We will harden `safe-sql-preview.ts` to strictly output valid DuckDB syntax.
- **Execution Orchestration Issue**: We will update `backend-preview-executor.ts` or `Investigation.tsx` to stop hiding behind fake HTTP errors and establish a legitimate local execution bridge or clearly surface execution blockers.
- **Out of Scope**: No WASM mounting assumptions unless a genuine WASM base exists. No UI redesigns. No changing the Understanding logic (Taxonomy, Aliasing).

## 4. Files to Modify
- `apps/desktop/src/pages/Investigation.tsx` (To handle actual execution states honestly).
- `apps/desktop/src/lib/backend-preview-executor.ts` (To replace or expose the phantom HTTP stub).
- `apps/desktop/src/lib/safe-sql-preview.ts` (To harden the DuckDB SQL dialect generation).
- `apps/desktop/src/lib/safe-sql-preview.test.ts` (To prove compilation correctness).

## 5. Acceptance Criteria
1. **Reduce Silent Fallbacks**: `Investigation.tsx` orchestration is fixed so that the primary backend path failure is correctly surfaced, preventing unnecessary silent drops to the JS sandbox for complex queries it cannot handle.
2. **SQL Validity**: Generated SQL syntax for `good_finance.csv` (`Revenue over Time Period`) strictly adheres to DuckDB quoting and function dialect.
3. **Honest Execution Propagation**: Executor errors are clearly propagated to the user instead of "Network failure" masking the real issue.
4. **No Guardrail Regression**: Ensures the strict boundary checks established in Runtime Truth checkpoints remain intact.
