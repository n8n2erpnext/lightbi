# Virtual Business View Real Data Audit

## 1. Where uploaded rows for each file are stored after multi-file intake
During the dataset selection phase, uploaded HTML5 `File` objects are stored in memory inside the `pendingLocalBatch.files` array. Their parsed preview rows (up to 100 rows per file) are generated by `local-file-inspector.ts` and stored deeply within `pendingLocalBatch.families[i].files[j].result.metadata.preview_rows`.

## 2. What `currentDataset` contains when `sourceType === "virtual_business_view"`
When a virtual business view is confirmed, the state variable `currentDataset` is populated with ONLY metadata:
- `status: 'ready'`
- `file_name`: The title of the business view
- `rows_count: null`
- `columns`: A flattened array of string names like `["family1.colA", "family2.colB"]`
- `profiles: {}`
- `sourceType: "virtual_business_view"`
- `selectedBusinessView`: The `BusinessViewCandidate` object containing the business view definition.

## 3. Whether `currentDataset` has real rows, row references, child dataset rows, profiles, or only metadata
It contains **only metadata**. The `rows` and `previewRows` properties are completely omitted. At the exact moment `currentDataset` is set for a virtual business view, `setPendingLocalBatch(null)` is called. This permanently drops the HTML5 `File` objects and the `preview_rows` arrays from memory. Consequently, the actual uploaded data is irrevocably lost.

## 4. What `selectedBusinessView.datasets` contains and whether those IDs can be resolved to rows
`selectedBusinessView.datasets` contains an array of dataset family IDs (e.g., `["fam_123", "fam_456"]`). Because `pendingLocalBatch` is destroyed, these IDs **cannot** be resolved to the underlying families, files, or rows. The mapping is broken.

## 5. Whether `VirtualDatasetPlan` contains enough information to select/join real rows
The `VirtualDatasetPlan` contains the array of dataset family IDs (`datasets: string[]`) and the relationship IDs needed to join them. However, it does **not** contain file paths, memory references, or the raw rows themselves. Without the rows preserved in state, the plan has the blueprint but no materials.

## 6. Why `executeDuckDBPreviewRuntime` is still disconnected/mock
`executeDuckDBPreviewRuntime` acts as a disconnected mock for two reasons:
1. The input parameter `PreviewRuntimeInput` does not accept raw rows. It only accepts metadata artifacts (`artifact`, `expectedResult`, `compiledQuery`, etc.).
2. The entire Virtual Business View pipeline drops the data early on. By the time execution is triggered, the UI simply doesn't have the uploaded rows to pass to any executor.

## 7. Smallest Viable Path to Real Execution
### Missing Data Structures & Logic
- **State:** A persistent `WorkspaceDataStore` that survives beyond `pendingLocalBatch` to hold `familyId -> previewRows` mappings.
- **SQL Compiler:** `safe-sql-preview.ts` is strictly hardcoded to generate `FROM __LIGHTBI_PREVIEW_TABLE__`. It lacks any logic to generate `JOIN` clauses.
- **Executor:** `local-duckdb-executor.ts` only accepts a single `rows` array and registers exactly one `data.json` file. It cannot register multiple files or execute joins.

### Conclusion: Real Virtual Execution is NOT FEASIBLE in this Phase
Because the entire backend compilation and execution stack (Planner, SQL Generator, Local Executor) fundamentally lacks the concept of multi-table joins, achieving real multi-file execution requires a major architectural rewrite spanning at least 5 layers.

### Recommended Smallest Fix
The most honest and viable path for this phase is to explicitly mark the flow as **preview-only/PARTIAL**.
1. Update `DuckDBPreviewRuntimeCard.tsx` to explicitly state `[PARTIAL]` and clearly display that the Virtual Business View preview is mock/contract-only.
2. Ensure the UI clearly communicates that real execution is not supported yet for Virtual Business Views.
3. Keep the Playwright test assertions strict but accept `[PARTIAL]` as the expected correct state for Group D, failing it if it claims `EXECUTED` when it is actually a mock.
